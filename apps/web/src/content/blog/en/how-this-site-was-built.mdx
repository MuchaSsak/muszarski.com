My old portfolio was a WebGL flight from Earth to Neptune. It looked good on my desktop and scored 34 on mobile Lighthouse. This site replaces it: Astro, three languages, one variable font, about 8 KB of JavaScript on the home page, and 99 to 100 on mobile Lighthouse. It was planned in a project wiki before any product code, its first design was thrown away, and every version since is kept, so this page can show you how it changed and why.

> **TL;DR**
>
> - **Before:** 13.8 MB downloaded before the start button, mobile performance 34, no touch or keyboard navigation, no indexable text.
> - **After (mobile, median of 3 runs):** home page Lighthouse 99 / 100 / 100 / 100, LCP about 1.95 s, CLS 0, page JavaScript about 8 KB gzip.
> - **How:** a wiki that every session reads, one design picked from four live options, my notes after every round, and screenshots, accessibility checks and Lighthouse on every slice.

## Why rebuild a site that people liked?

The space portfolio was my favourite thing to show and the worst thing to send to a recruiter. I measured it on 5 October 2026:

| Measure | Old site |
| --- | --- |
| Downloaded before the "start" button | 13.8 MB (7.6 MB of it an emoji font) |
| Lighthouse performance, mobile | 34 (LCP 46.9 s) |
| Lighthouse performance, desktop | 60 (total blocking time 1,240 ms) |
| Navigation | mouse wheel only: no touch swipe, no keyboard |
| On a phone | an "Oops!" screen |
| Text in the raw HTML | none a search engine could index |

A person who opens a portfolio from a LinkedIn message on a phone gets maybe ten seconds. My site spent them on a loading bar. It proved I can write shaders; it also proved I hadn't thought about the person on the other side.

## What did the new site have to do?

One rule, written down before choosing a framework: **impressive within 3 seconds, and usable in one tap on a phone.** No preloader, no gate, no scroll-jacking, the same content on mobile as on desktop. The budgets came from it:

- Lighthouse mobile at least 90 on every page; LCP under 2.5 s (target 2.0), CLS under 0.05
- under 150 KB of JavaScript and under 100 KB of fonts on first load
- the main heading is the largest contentful paint, so it renders final from the server
- WCAG 2.2 AA, and a pause button for anything that moves longer than five seconds
- English, Polish and Spanish, with the CV page and the PDF generated from one data file

## How did the planning work?

Before a single component existed, I spent a session building a wiki in `.claude/project-info/`: about thirty pages, each owning one kind of fact. Every non-obvious fact carries its source: `[user]` when I decided it, `[research]` when an agent found it, `[assumption]` when nobody knows yet.

Three hooks keep it alive. One loads the rules and the lessons when a session starts or after compaction. One routes the right pages into each prompt. One blocks the end of a turn when code changed but the wiki didn't. The method is in [An LLM wiki: project memory for Claude Code](/en/blog/llm-wiki-project-memory-for-claude-code/).

The payoff showed up later. When I changed my mind, there was one place to change it. When a session lost its memory to compaction, the next one read the same pages and carried on.

## Why Astro and not Next.js?

A portfolio is a content site: a few pages, mostly static, where every kilobyte of JavaScript costs the person on a slow phone. Astro renders components to HTML and ships no JavaScript unless a component asks for it. Lingui works in Astro through `lingui-for-astro`, and a missing Polish or Spanish string fails the build. The longer version is in [Astro vs Next.js for a portfolio](/en/blog/astro-vs-nextjs-for-a-portfolio/).

## How does the name fill the screen with no JavaScript?

The hero name runs edge to edge at every width, and it is the largest contentful paint, so it can't wait for a script to measure it.

The font is Anybody, a variable font with a width axis from 50 to 150. At build time a script measures every glyph's advance and the kerning at both ends of that axis. Between them the width of a line changes linearly, so for each line I can solve for the exact width setting that fills its box. The page ships that as CSS: `font-size` in container query units and `font-stretch` per line. No measuring in the browser, no layout shift. The full technique is in [Fit text to its container at build time](/en/blog/fit-text-to-width-at-build-time/).

## How is the motion kept cheap and safe?

The site moves a lot: a spinning sticker, a marquee of tools, product loops, a ring that walks through how I work. Every piece follows the same rules:

- it pauses when its section is off screen
- one "Pause motion" button stops everything, and the choice is remembered (WCAG 2.2.2)
- with reduced motion requested, everything shows its final state
- entrances never hide content: the first paint is the finished page

That last rule came from a live bug: on a cold first visit, staged entrances left only my name on screen for up to a second. Now an entrance is a short settle of a few pixels, never a fade from nothing. More in [the reduced-motion post](/en/blog/reduced-motion-and-a-pause-button/).

## What does the AI workflow look like day to day?

I run Claude Code like a small team with a strict lead. A request comes in as plain words; the hooks route the relevant wiki pages into it; research and drafts fan out to subagents in parallel; MCP servers give the agent a real browser, real app screens and a component registry; skills hold the playbooks for screenshots, Lighthouse and commits.

The checks are the floor: type checking, lint, unit tests, Playwright end-to-end tests with axe, a layout sweep from 320 to 2560 pixels, and Lighthouse. A change isn't done until they pass and I've looked at the screenshots myself. When something goes wrong, it becomes a one-line rule in the lessons file, and the next session loads it at start. The AI does a lot of the typing; I own the decisions and anything that ships under my name. The [building blocks post](/en/blog/claude-code-skills-hooks-mcp-subagents/) has the details.

## What did it cost?

Each slice records what it spent of the budgets: the home page after each step, mobile Lighthouse with simulated throttling, median of three runs.

| Slice | HTML (gzip) | Page JavaScript | Fonts | LCP | CLS |
| --- | --- | --- | --- | --- | --- |
| First design, foundation | 7.7 KB | about 1 KB | 47.2 KB in 4 files | 1.05 s | 0 |
| First design, header and footer | 10.7 KB | 0.8 KB | 47.2 KB | 1.21 s | 0.011 |
| Poster: header, hero, tool band, footer | 22.9 KB | 3.0 KB | 49.5 KB in 1 file | 1.65 s | 0 |
| Poster: every section | 38.1 KB | about 9 KB | 49.9 KB in 1 file | 1.95 s | 0 |
| Poster after a feedback round (fewer scripts) | 34.7 KB | about 8 KB | 49.9 KB in 1 file | 1.95 s | 0 |

The LCP went up when Poster arrived: the heading now waits for one variable font instead of a small static cut. A trace showed the rest: the browser holds the first paint until the preloaded font arrives, and the font shares the connection with the HTML. Moving the icon paths into one cached sprite file cut the HTML from 54.5 to 38.1 KB gzip and the LCP from 2.03 to 1.95 s.

## What would I do differently?

- **Show directions before building.** I froze the first design before seeing an alternative and paid two slices of work for a look I threw away.
- **Write the budget into the first commit.** Measuring from the first slice made every later trade-off a number instead of an opinion.
- **Record the product videos earlier.** Two project chapters still use drawn stand-ins, and a drawing explains less than ten seconds of the real thing.

## Results, and how they were measured

- Lighthouse, mobile, simulated throttling, median of three runs on a local production build: the home page scores 99 for performance and 100 for accessibility, best practices and SEO, in all three languages.
- On the home page: LCP about 1.95 s, CLS 0, total blocking time 0-15 ms, about 8 KB gzip of page JavaScript, one 50.4 KB font file.
- End-to-end tests with axe; no horizontal scrolling from 320 to 2560 pixels.

Real-user data will come after launch. Until then these are lab numbers, and I treat them that way.

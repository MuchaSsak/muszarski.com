My old portfolio was a WebGL flight from Earth to Neptune. It looked good on my desktop and scored 34 on mobile Lighthouse. This site replaces it: Astro, three languages, one variable font, about 8 KB of JavaScript on the home page, and 95 to 100 on mobile Lighthouse. It was planned in a project wiki before any product code, its first design was thrown away, and every version since is kept, so this page can show you how it changed, which tools did the work, and why.

> **TL;DR**
>
> - **Before:** 13.8 MB downloaded before the start button, mobile performance 34, no touch or keyboard navigation, no indexable text.
> - **After (mobile, median of 3 runs):** home page Lighthouse 95 / 100 / 100 / 100, every other page I measured 96 to 100, page JavaScript about 8 KB gzip.
> - **How:** a project wiki that every Claude Code session reads first, research on award-winning portfolios and real product screens, four live designs to pick from, and Playwright, axe and Lighthouse on every change.

## Why rebuild a site that people liked?

The space portfolio was my favourite thing to show and the worst thing to send to a recruiter. I measured it on 5 October 2026:

| Measure | Old site |
| --- | --- |
| Downloaded before the "start" button | 13.8 MB (7.6 MB of it an emoji font) |
| Lighthouse performance, mobile | 34 (LCP 46.9 s) |
| Lighthouse performance, desktop | 60 (total blocking time 1,240 ms) |
| Navigation | mouse wheel only: no touch swipe, no keyboard |
| On a phone | an "Oops!" screen |
| Text in the raw HTML | none a search engine could index |

A person who opens a portfolio from a LinkedIn message on a phone gets maybe ten seconds. My site spent them on a loading bar. It proved I can write shaders; it also proved I hadn't thought about the person on the other side.

## What did the new site have to do?

One rule, written down before choosing a framework: **impressive within 3 seconds, and usable in one tap on a phone.** No preloader, no gate, no scroll-jacking, the same content on mobile as on desktop. The budgets came from it:

- Lighthouse mobile at least 90 on every page; LCP under 2.5 s (target 2.0), CLS under 0.05
- under 150 KB of JavaScript and under 100 KB of fonts on first load
- the main heading is the largest contentful paint, so it renders final from the server
- WCAG 2.2 AA, and a pause button for anything that moves longer than five seconds
- English, Polish and Spanish, with the CV page and the PDF generated from one data file

## What is it built with?

A portfolio is a content site: a few pages, mostly static, where every kilobyte of JavaScript costs the person on a slow phone. So the stack is chosen to send HTML first and as little script as possible.

| Layer | Tool | Why this one |
| --- | --- | --- |
| Framework | Astro 7 | Renders components to HTML and ships no JavaScript unless a component asks for it |
| Language and styling | TypeScript, Tailwind CSS 4, design tokens in CSS | Types across data, pages and scripts; one set of colour and spacing tokens |
| Translations | Lingui with `lingui-for-astro` | Every string goes through one catalog per language; a missing Polish or Spanish string fails the build |
| Repo | Turborepo and bun | The site and its shared package in one repo, cached builds |
| Type | Anybody, a variable font (OFL) | One 50 KB file with a width axis, which the fitted headings need |
| Icons | Tabler (MIT) and Simple Icons (CC0) | Built into one cached sprite file instead of paths in every page |
| Hosting | Vercel | Static pages plus one small function for the contact form |
| Contact | EmailJS called from that function, Cloudflare Turnstile | The keys never reach the browser, and bots get stopped before a send |
| Analytics | Umami Cloud | Cookieless, so no consent banner |
| Tests | Playwright, axe-core, Vitest, Lighthouse | Browsers, accessibility, logic and speed, all from scripts |

Playwright does more than tests here. The same browser prints the CV PDF from the `/cv/` page (so the page and the PDF can't drift apart), renders the share image for every page, and takes the screenshots I review. The longer comparison with Next.js is in [Astro vs Next.js for a portfolio](/en/blog/astro-vs-nextjs-for-a-portfolio/).

## How did the planning work?

In April 2026 Andrej Karpathy published a short idea file called [LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f). The idea: instead of an AI searching your raw documents again on every question, it keeps a wiki of markdown pages that it writes and updates itself, so what it learns builds up instead of being found again each time. He describes three layers (the raw sources, the wiki, and a schema with the rules) and three jobs: take in new sources, answer from the wiki, and check it for drift.

I used that pattern as the memory of this project. Before a single component existed, I spent a session building a wiki in `.claude/project-info/`: about thirty pages, each owning one kind of fact, from the audience and the brand to the legal texts and the budgets. Every non-obvious fact carries its source: `[user]` when I decided it, `[research]` when an agent found it, `[assumption]` when nobody knows yet.

Pages only help if they get read, so three Claude Code hooks deliver them:

### What did 20 award-winning portfolios teach?

Three findings shaped this site:

- **An award doesn't mean the site is usable.** The four least practical sites (game worlds and gated intros) had a higher average Site of the Day score than the three most practical ones. On the throttled phone, 9 of the 20 weren't usable within 10 seconds.
- **Stunning and practical is possible, but rare.** Only [Edoardo Lunardi](https://edoardolunardi.dev/), [Jesper Landberg](https://jesperlandberg.com/), [Antoine Wodniack](https://wodniack.dev/) and Stefan Vitasović scored 4 or more on both. What they share: real links on the first paint, and the show as a layer beside the content, never a gate in front of it.
- **One signature effect is enough.** Wodniack's whole site is 0.48 MB around one line effect. That's where "the name is the picture" came from: one strong typographic moment instead of a 3D world.

Smaller things came from single sites: a "Hire me" button in the header (Wodniack), the CV one click away in the header (Valentin Mor), an `/llms.txt` file for AI crawlers (Jesper Landberg), and a skip link, which only 2 of the 20 had. When my first design was rejected, a second pass rendered 41 more sites and boiled ambition down to four levers: one dominant element, a saturated full-bleed colour, depth with overlaps, and motion that turns into the content. Poster uses all four.

I don't show screenshots of those sites here: they are other people's work. The names link to the real thing.

### What did Mobbin add?

[Mobbin](https://mobbin.com/) is a library of real screens from shipped apps and sites, and Claude Code can search it through its MCP server. The rule in the wiki: research each section on Mobbin before designing it. About twenty searches covered the sections and the inner pages: device frames, process steps, credential lists, contact forms, an article page, a privacy page.

It's strongest on product (SaaS) sections and weakest on portfolio heroes, so most of what it found shaped individual sections, not the look. The clearest example that survived to this site is the contact form: the "A job / A project / A question" chips above the message box come from the reason chips on United Carriers' contact page. They let you start with one tap instead of a blank field.

### Why install nothing from the component registries?

A Claude Code skill searches public shadcn registries (through the Shoogle MCP server) for a ready component: a copy button, a lightbox, a table of contents, a phone frame, a marquee, a terminal. About twenty searches and fifteen candidates later, I installed none of them. The shortlist was useful as a reference for behaviour and geometry, but each piece would have brought its own dependencies and styling into a site that has a JavaScript budget and its own design system. Writing twenty lines that fit was cheaper than adapting two hundred that didn't. Searching first still paid off: it showed what a good version of each piece looks like before I wrote mine.

## How does the name fill the screen with no JavaScript?

The hero name runs edge to edge at every width, and it is the largest contentful paint, so it can't wait for a script to measure it.

The font is Anybody, a variable font with a width axis from 50 to 150. At build time a script measures every glyph's advance and the kerning at both ends of that axis. Between them the width of a line changes linearly, so for each line I can solve for the exact width setting that fills its box. The page ships that as CSS: `font-size` in container query units and `font-stretch` per line. No measuring in the browser, no layout shift. The full technique is in [Fit text to its container at build time](/en/blog/fit-text-to-width-at-build-time/).

## How is the motion kept cheap and safe?

The site moves a lot: a spinning sticker, a marquee of tools, product loops, a ring that walks through how I work, a story of seven steps. Every piece follows the same rules:

- it pauses when its section is off screen
- one "Pause motion" button stops everything, and the choice is remembered (WCAG 2.2.2)
- with reduced motion requested, everything shows its final state
- entrances never hide content: the first paint is the finished page

That last rule came from a live bug: on a cold first visit, staged entrances left only my name on screen for up to a second. Now an entrance is a short settle of a few pixels, never a fade from nothing. More in [the reduced-motion post](/en/blog/reduced-motion-and-a-pause-button/).

## What does the AI workflow look like day to day?

I run Claude Code like a small team with a strict lead. A request comes in as plain words; the hooks route the relevant wiki pages into it; research and drafts fan out to subagents in parallel; MCP servers give the agent a real browser, real app screens and the component registries; skills hold the playbooks for the code loop, Lighthouse fixes, the wiki lint and commits.

A change isn't done until the checks pass and I've looked at the screenshots myself. The AI does a lot of the typing; I own the decisions and anything that ships under my name. The [building blocks post](/en/blog/claude-code-skills-hooks-mcp-subagents/) has the details.

The LCP went up when Poster arrived: the heading now waits for one variable font instead of a small static cut. A trace showed the rest: the browser holds the first paint until the preloaded font arrives, and the font shares the connection with the HTML. Moving the icon paths into one cached sprite file cut the HTML from 54.5 to 38.1 KB gzip and the LCP from 2.03 to 1.95 s.

## What would I do differently?

- **Show directions before building.** I froze the first design before seeing an alternative and paid two slices of work for a look I threw away.
- **Write the budget into the first commit.** Measuring from the first slice made every later trade-off a number instead of an opinion.
- **Record the product videos earlier.** Two project chapters still use drawn stand-ins, and a drawing explains less than ten seconds of the real thing.

## Results, and how they were measured

- Lighthouse, mobile, simulated throttling, median of three runs on a local production build (7 October 2026): the home page scores 95 to 96 for performance and 100 for accessibility, best practices and SEO; this post, the CV and the blog score 98 to 100.
- On the home page: LCP about 2.1 s, CLS 0, about 8 KB gzip of page JavaScript, one 50 KB font file. The live site measured 99 with an LCP of 1.78 s.
- 236 end-to-end tests with axe, the core flows in Firefox and WebKit too, and no horizontal scrolling from 320 to 2560 pixels.

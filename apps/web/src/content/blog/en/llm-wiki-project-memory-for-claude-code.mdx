An LLM wiki is a folder of small markdown pages inside your repo that the agent reads instead of asking you again. Mine lives in `.claude/project-info/`: CLAUDE.md routes each task to the right pages, hooks inject those pages per prompt and reload the lessons after every compaction, and a Stop hook won't let a session finish a code change without updating the wiki.

## Why a wiki and not a bigger CLAUDE.md

The memory docs start with the problem: "Each Claude Code session begins with a fresh context window." Long sessions have a second one. Compaction summarizes the conversation to free space, and the hooks guide warns it "can lose important details". Anything you only said in chat goes first: the docs' troubleshooting section says that if an instruction disappeared after compaction, "it was given only in conversation".

The obvious fix is to write everything into CLAUDE.md. It survives compaction: the context window docs show it reloading next to auto memory, the most recently modified files and the skills you invoked, while the conversation itself becomes a summary. But CLAUDE.md loads in full on every request, and the docs suggest staying under 200 lines because "longer files consume more context and reduce adherence". Imports don't help: imported files also load at launch.

A portfolio with a brand voice, a design system, three locales, legal pages and a CV has far more than 200 lines of facts. So the facts go into a wiki, and CLAUDE.md becomes its index.

## Where the idea comes from

Andrej Karpathy published the pattern in April 2026 as an "idea file" called llm-wiki. In his version the LLM "incrementally builds and maintains a persistent wiki" of markdown files that sits between you and your raw sources. It has three layers (raw sources, the wiki, and a schema document such as CLAUDE.md), three operations (ingest, query, lint), an `index.md` catalogue and an append-only `log.md`.

My setup follows the same idea, pointed at one software project instead of a research topic. Three things differ:

1. The raw sources are me, the repo and dated research notes.
2. The wiki steers an agent that writes code, so it holds rules (a working agreement, lessons), not only knowledge.
3. Hooks deliver the right pages automatically. I don't rely on the agent remembering to read the index.

My log entries use the same `## [date] area | summary` shape the gist suggests, which keeps them greppable.

## The layout

```text
.claude/project-info/
├─ README.md · working-agreement.md · lessons.md
├─ open-questions.md · placeholders.md · log.md
├─ product/   why and what: brief, requirements, audience, voice
├─ content/   what the site says: content model, projects
├─ site/      structure, SEO, i18n, analytics
├─ design/    design system, references, quality rubric, assets
├─ tech/      stack, conventions, one how-to page per library
├─ legal/     facts behind the legal pages
├─ memory/    measured numbers
└─ research/  raw dated notes (not routed)
```

As I write this, that is 33 pages outside `research/`. The root files stay at the root because the hooks look for them there. Everything else is grouped by the question it answers: why, what, how it's organised, how it looks, how it's built.

## Rules that keep it honest

- **One owner per fact.** Each fact lives in one page and the others link to it. Copies drift apart.
- **Facts carry their source.** `[user]` for my decisions, `[research]` for findings, `[repo: path]` for what the code says, `[assumption]` for a guess. A guess gets revisited, a decision doesn't. Today the wiki holds 95 `[user]`, 100 `[research]` and 83 `[assumption]` tags. The last number is the honest one: a lot of the project still runs on defaults I haven't confirmed.
- **Unknown beats invented.** A missing fact is written as Unknown and goes to `open-questions.md`, a table of question, what it blocks, who answers, the default if nobody does, and status. It has 46 rows.
- **Not-real things are registered.** Every placeholder gets a row in `placeholders.md`, and "go to production" means clearing that list first.
- **Dense, not long.** Tables and short bullets, roughly 40-150 lines a page. A page you can skim in a minute gets read.
- **The code wins.** When a page and the code disagree, the page gets fixed.

## The machinery

### CLAUDE.md as a router

My CLAUDE.md is 76 lines: a routing table, ten invariants and the commands. Each row pairs the words people actually type with the pages to read:

```markdown
| Task touches | Read |
| --- | --- |
| Locales, translation, Lingui, Polish, Spanish, language switcher, hreflang | `.claude/project-info/site/i18n.md` |
| Code style, folders, git, commits, testing bar, do-not list | `.claude/project-info/tech/conventions.md` |
```

The paths are plain text on purpose. An `@import` would load the whole wiki into every session.

### Routing per prompt

A UserPromptSubmit hook runs before Claude processes each prompt, and the docs say its output is added to Claude's context. Mine scores the prompt's words against each row. An exact match counts 1, a plural 0.9, a shared prefix of five or more letters 0.6. Each score is divided by the square root of how many rows contain that word, so words that appear everywhere count for little. At most five rows get injected. A small JSON file maps Polish word stems to table words, so Polish prompts route too. The hook's test mode shows the result:

```text
> przetłumacz stopkę na hiszpański
  1.00  Pages, sitemap, home sections, hero, header, navigation, footer...  [footer]
  1.00  Locales, translation, Lingui, Polish, Spanish, language switcher...  [spanish]
> where did I leave that
  (nothing routed)
```

### The session card

SessionStart fires on startup, on resume, after `/clear` and after compaction, and the hook receives which one it was. The hooks guide recommends this for compaction: use a SessionStart hook with a `compact` matcher "to re-inject critical context after every compaction". Mine prints a short note for the occasion (after compaction: "This is not a pause: carry on with the current task", then re-read files before editing and check git), a pointer to the working agreement, the git state as counts only, and the `## Rules` section of `lessons.md`, capped at 8,000 characters.

### The Stop check

When Claude finishes a turn, a Stop hook compares what changed in the session (commits since the session's starting point, plus the working tree) with what changed in the wiki. If code changed and the wiki didn't, it blocks the stop once, with a reason that lists the steps: update the page that describes the change, append to `log.md`, record a lesson, or say in one line that nothing documented changed. If the wiki changed, it runs the lint and blocks on errors.

The docs give you two loop guards: the `stop_hook_active` input and a cap on consecutive continuations. My script adds a third: it remembers the state it last blocked on, so the same diff never blocks twice.

## The lessons loop

If I had to drop everything else, I'd keep `lessons.md`. When I correct Claude, or a tool trips it, the fix becomes one imperative line with a date under `## Rules`:

```markdown
- Git Bash rewrites URL-path arguments (`/en/` -> `P:/Git/en/`): prefix such
  commands with `MSYS_NO_PATHCONV=1` - 2026-10-05.
```

The session card injects that section, so every new session and every compaction starts with all the rules. There are 39 now, about 7,200 characters, under a cap of 60. A rule that keeps coming back gets promoted into a check (a test, a lint rule, a hook), because enforced beats remembered.

Claude Code also has built-in auto memory: notes Claude writes for itself, indexed in a `MEMORY.md` whose first 200 lines or 25 KB load at every session start. The docs describe it as machine-local. The lessons file lives in git instead, so I review its changes in diffs like code.

## How to start one

1. Run `/init` or write a short CLAUDE.md by hand: commands and non-negotiables.
2. Create `.claude/project-info/` with five root files: `README.md` (the map), `working-agreement.md`, `lessons.md`, `open-questions.md`, `log.md`.
3. Add pages only when the project needs them. A CLI doesn't need a brand page.
4. Write the routing table in the words you actually type, synonyms included.
5. Add hooks one at a time: SessionStart first (lessons after compaction), then routing, then the Stop check.
6. Test routing with five realistic prompts and one noise prompt that should route nowhere.
7. End every task the same way: verify, update the page, append to the log, add a lesson if you were corrected.

I packaged steps 2-6 as a skill, so a new project starts with the same machinery. When I set up this repo, the routing test used 15 prompts, including 4 in Polish and one noise prompt.

## What went wrong, and the limits

- **Drift is real.** The wiki is only as true as its last update. One read-through as a stranger, when the wiki had 26 pages, found about 40 contradictions between pages. The Stop hook proves that something in the wiki changed, not that it's right.
- **Routing misses.** It is keyword scoring, not meaning. A generic phrase in one row once outscored a project name in another and cut the page that mattered. The fix: put shared task words in every row they apply to, then re-run the test.
- **It costs tokens and time.** The session card puts about 7,200 characters of rules into every session, and every task ends with documentation work. I haven't measured the net saving. What I can say is that I stopped repeating myself after compactions.
- **It's advice, not enforcement.** The docs are clear that CLAUDE.md is context, not configuration, and the wiki is the same. Anything that must hold every time belongs in a hook or a test.
- **It can leak.** A wiki in git is a wiki someone might read. Name environment variables, never their values. My lint scans the wiki for key-shaped strings.

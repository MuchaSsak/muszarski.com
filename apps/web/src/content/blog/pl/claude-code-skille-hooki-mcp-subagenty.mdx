CLAUDE.md trzyma to, co Claude ma wiedzieć w każdej sesji. Skill to procedura albo materiał referencyjny potrzebny tylko czasem, a hook to coś, co musi się wydarzyć za każdym razem. Serwer MCP sięga po dane i akcje spoza repozytorium, a subagent bierze na siebie poboczną robotę, której wynik zaśmieciłby główny kontekst. Niżej rozkładam każdy element na części według oficjalnej dokumentacji Claude Code i pokazuję, jak połączyłem je przy budowie tej strony.

## Pięć elementów w pigułce

Strona dokumentacji „Extend Claude Code” opisuje całą warstwę rozszerzeń. W skrócie:

- **CLAUDE.md** to plik markdown wczytywany na starcie każdej sesji: komendy, konwencje, zasady typu „zawsze rób X”. Dokumentacja radzi trzymać każdy taki plik poniżej 200 linii.
- **Skill** to plik `SKILL.md` w `.claude/skills/<nazwa>/` z instrukcjami, wiedzą albo workflowem. Uruchamiasz go przez `/nazwa` albo Claude sam go wczytuje, gdy opis pasuje do zadania. Własne komendy slash zostały scalone ze skillami.
- **Hook** to coś, co Claude Code uruchamia przy zdarzeniu z cyklu życia sesji: start, wysłanie promptu, przed użyciem narzędzia, zakończenie odpowiedzi i wiele innych. Może to być komenda powłoki, zapytanie HTTP, wywołanie narzędzia MCP, prompt albo subagent.
- **Serwer MCP** łączy Claude Code z zewnętrznymi narzędziami i danymi przez Model Context Protocol, otwarty standard.
- **Subagent** pracuje we własnym oknie kontekstu, z własnym promptem systemowym i dostępem do narzędzi. Robi swoje i oddaje tylko podsumowanie.

Są jeszcze pluginy, które pakują to wszystko w jedną instalowalną całość do użycia w wielu repozytoriach. Tutaj ich nie używam, więc je pomijam.

## Dwa pytania, które rozstrzygają prawie wszystko

**Kto decyduje, że coś się uruchomi?** Dokumentacja mówi wprost: hook zawsze odpala się na swoim zdarzeniu, a skill to instrukcje, które Claude interpretuje, więc wynik może się różnić. CLAUDE.md należy do tej drugiej grupy: według dokumentacji pamięci Claude traktuje go jako kontekst, a nie wymuszoną konfigurację. Stąd najważniejsza zasada z tej strony: „nigdy nie edytuj `.env`” w CLAUDE.md to prośba, a hook `PreToolUse`, który blokuje edycję, to egzekwowanie.

**Ile to kosztuje w kontekście?** Według tabeli kosztów z dokumentacji:

| Element | Kiedy się wczytuje | Koszt w kontekście |
| --- | --- | --- |
| CLAUDE.md | start sesji, cała treść | przy każdym zapytaniu |
| Skill | opisy na starcie, treść przy użyciu | niski, dopóki nie jest użyty |
| Serwer MCP | nazwy narzędzi na starcie, schematy na żądanie | niski, dopóki narzędzie nie jest użyte |
| Subagent | przy uruchomieniu, we własnym oknie | odizolowany od głównej sesji |
| Hook | przy zdarzeniu, poza modelem | zero, chyba że zwraca kontekst |

Dlatego długi CLAUDE.md to złe miejsce na dokumentację referencyjną: płacisz za nią przy każdym zapytaniu, potrzebna czy nie. Treść skilla prawie nic nie kosztuje, dopóki ktoś po nią nie sięgnie.

## Potrzeba → element

| Potrzebujesz | Wybierz | Dlaczego |
| --- | --- | --- |
| Żeby Claude zawsze znał komendy i konwencje | CLAUDE.md | wczytywany zawsze |
| Procedury ze skutkami ubocznymi, którą odpalasz sam | skill z `disable-model-invocation: true` | uruchamiasz go tylko Ty, a jego opis nie zajmuje kontekstu |
| Wiedzy w tle, z której Claude skorzysta w razie potrzeby | skill, `user-invocable: false`, jeśli to nie komenda | wczytywany na żądanie |
| Czegoś przy każdej edycji, prompcie albo końcu odpowiedzi | hook | deterministyczny |
| Zablokowania groźnej akcji | hook `PreToolUse` albo reguły uprawnień | egzekwowanie, a nie prośba |
| Danych z systemu, którego Claude nie widzi | serwer MCP | połączenie i autoryzacja po stronie serwera |
| Researchu po wielu plikach albo pracy równoległej | subagent | wraca tylko podsumowanie |
| Częstej wymiany zdań nad jednym problemem | główna rozmowa | tu dokumentacja odradza subagenty |

Dokumentacja radzi też dokładać elementy dopiero wtedy, gdy pojawi się konkretny sygnał. Claude drugi raz myli konwencję: wpis do CLAUDE.md. Trzeci raz wklejasz ten sam playbook: skill. Ciągle kopiujesz dane z karty przeglądarki: serwer MCP. Poboczne zadanie zalewa rozmowę: subagent. Coś ma się dziać zawsze, bez proszenia: hook.

## Mój zestaw, element po elemencie

Ta strona powstała w Claude Code sterowanym przez wiki projektu w `.claude/project-info/`. Oto co robi każdy element w tym repozytorium.

### CLAUDE.md: rozdzielnik, a nie encyklopedia

Mój CLAUDE.md ma 76 linii. Większość to tabela routingu: 31 wierszy, które łączą słowa, jakich używam w poleceniach („locales, translation, hreflang”), ze stronami wiki. Do tego dziesięć niezmienników, na przykład budżety wydajności, licencje i „żadnych zmyślonych faktów”. Ścieżki są celowo zwykłym tekstem. `@import` wczytałby każdą stronę do każdej sesji, a dokumentacja potwierdza, że importy nie zmniejszają kosztu kontekstu. Samo wiki opisuję w osobnym wpisie: [LLM wiki, czyli pamięć projektu dla Claude Code](/pl/blog/llm-wiki-pamiec-projektu-dla-claude-code/).

### Trzy hooki

```json
{
  "hooks": {
    "SessionStart": [{ "hooks": [{ "type": "command",
      "command": "node .claude/hooks/session-start.mjs", "timeout": 10 }] }],
    "UserPromptSubmit": [{ "hooks": [{ "type": "command",
      "command": "node .claude/hooks/wiki-context.mjs", "timeout": 10 }] }],
    "Stop": [{ "hooks": [{ "type": "command",
      "command": "node .claude/hooks/wiki-check.mjs --stop-hook", "timeout": 30 }] }]
  }
}
```

To wersja skrócona: w prawdziwym `.claude/settings.json` każda ścieżka zaczyna się od `${CLAUDE_PROJECT_DIR:-.}`, a komendy idą przez bash.

- **SessionStart** wypisuje „kartę sesji”: odnośnik do zasad współpracy, stan gita (same liczby) i reguły z `lessons.md`. To zdarzenie odpala się na starcie, przy wznowieniu, po `/clear` i po kompaktowaniu, a Claude Code dokleja wynik hooka do kontekstu. Po każdym kompaktowaniu reguły wracają więc słowo w słowo, cokolwiek zgubiło podsumowanie.
- **UserPromptSubmit** ocenia każdy prompt względem tabeli routingu i podaje do pięciu stron do przeczytania. Prompty krótsze niż 25 znaków niczego nie dostają.
- **Stop** sprawdza, czy w tej sesji zmienił się kod bez zmiany w wiki. Jeśli tak, zwraca `decision: "block"` z powodem, raz na dany stan, więc Claude aktualizuje stronę opisującą zmianę, zanim skończy. Gdy `stop_hook_active` ma wartość true, hook od razu się kończy: to pole dokumentacja daje właśnie po to, żeby hook Stop nie blokował w nieskończoność.

Wszystkie trzy to zwykłe skrypty Node, które przy własnym błędzie kończą się bez szkody dla sesji. Strażnik, który psuje sesję, jest gorszy niż brak strażnika.

### Siedem skilli

| Skill | Kto uruchamia | Co robi |
| --- | --- | --- |
| `code` | ja albo Claude | pętla kodowania: przeczytaj wskazane strony, dopasuj się do kodu, sprawdź przed ogłoszeniem „gotowe” |
| `commit` | ja albo Claude | jeden Conventional Commit, przypięty do małego modelu Haiku, żeby szło szybko |
| `lighthouse-qa` | ja albo Claude | puszcza Lighthouse na zbudowanej stronie i poprawia w pętli, aż każda strona zmieści się w budżecie |
| `wiki-lint` | ja albo Claude | uruchamia mechaniczny lint wiki, a potem czyta strony pod kątem sprzeczności |
| `awwwards` | tylko Claude | ogląda nagradzane strony w prawdziwej przeglądarce, żeby podnieść jedną płaską sekcję |
| `search-registry-items` | tylko Claude | szuka komponentu w publicznych rejestrach shadcn przez serwer MCP i go instaluje |
| `start-project-info` | tylko ja | zakłada wiki, tabelę routingu, lekcje i hooki w nowym projekcie |

„Tylko Claude” to `user-invocable: false`: wiedza w tle, która nie ma sensu jako komenda. „Tylko ja” to `disable-model-invocation: true`: ten skill zapisuje sporo plików, więc wolę go odpalać sam, a do tego czasu jego opis nie kosztuje nic w kontekście. Strona główna ma dziś 100 we wszystkich czterech kategoriach mobilnego Lighthouse (mediana z 3 pomiarów), a `lighthouse-qa` to pętla, która tego pilnuje.

### Trzy serwery MCP

- **Mobbin**, biblioteka referencji UI i UX z aplikacji mobilnych i stron. Jej serwer MCP pozwala agentowi przeszukiwać bibliotekę językiem naturalnym i dostawać zrzuty ekranów. Korzystałem z niego przy researchu sekcji, zanim je projektowałem.
- **Shoogle**, wyszukiwarka bloków shadcn/ui w wielu rejestrach. Skill `search-registry-items` mówi Claude'owi, kiedy po nią sięgnąć.
- **Prawdziwa przeglądarka.** Playwright MCP steruje przeglądarką przez snapshoty drzewa dostępności, a Claude in Chrome łączy Claude Code z samym Chrome i korzysta z jego stanu logowania.

Dokumentacja MCP ma ostrzeżenie, które warto powtórzyć: upewnij się, że ufasz każdemu serwerowi, bo te, które pobierają treści z zewnątrz, narażają Cię na prompt injection.

### Subagenty

Nie mam własnych definicji subagentów, wbudowane wystarczyły. Używałem ich do researchu na etapie planowania: log wiki odnotowuje jedną partię 8 agentów badawczych i jedną 3, każdy z osobnym tematem. Zapisywały surowe notatki, a ja przenosiłem wnioski do stron, do których prowadzi routing. Wyszła z tego jedna lekcja: równoległe agenty dzielą jeden budżet wyszukiwania w sieci i potrafią go wyczerpać, więc lepiej pobierać adresy, które już znasz.

## Jak to się łączy

Elementy robią się naprawdę przydatne, kiedy łatają nawzajem swoje słabe strony.

- **Skill + MCP.** Serwer daje Claude'owi narzędzie, a skill mówi, kiedy warto po nie sięgnąć i co zrobić z wynikiem. Dokumentacja opisuje dokładnie ten wzorzec.
- **CLAUDE.md + hook.** Tabela routingu to zwykły markdown, który sam czytam i edytuję. Hook promptu parsuje tę samą tabelę, więc nowy wiersz wystarczy, żeby nowa strona trafiała do właściwych zadań.
- **Hook + skill.** `wiki-check.mjs` to część mechaniczna: ścieżki istnieją, każda strona jest w spisie, wpisy w logu mają właściwy format. Skill `wiki-lint` to część wymagająca osądu: czy dwie strony sobie przeczą? Skrypt nie oceni sensu, a na modelu nie można polegać, że uruchomi się za każdym razem.
- **Skill + subagent.** Skill może działać w osobnym kontekście subagenta (`context: fork`), a subagent może mieć wczytane skille z góry. Na razie nie potrzebowałem ani jednego, ani drugiego.

## Błędy i ograniczenia

- **Hooki działają z pełnymi uprawnieniami Twojego użytkownika.** Dokumentacja hooków mówi to otwarcie. Przeczytaj każdy hook, zanim go dodasz, zwłaszcza skopiowany z cudzego repozytorium.
- **Opisy skilli nie są darmowe.** Każdy skill, który Claude może sam wywołać, trzyma opis w kontekście, a lista ma swój budżet. Gdy się przepełni, Claude Code wycina opisy skilli używanych najrzadziej. Mętne albo nakładające się opisy sprawiają też, że Claude wybiera nie ten skill.
- **Routing po słowach kluczowych się myli.** Mój hook liczy słowa, a nie znaczenie. Na początku ogólna fraza w jednym wierszu przebiła nazwę projektu w innym i wycięła stronę, która była potrzebna. Poprawka była nudna: wspólne słowa zadań wpisać do każdego wiersza, którego dotyczą, i ponownie uruchomić tryb `--test`.
- **Subagent zaczyna od zera.** Nie widzi Twojej rozmowy, tylko wiadomość z poleceniem, więc mętne zlecenie wraca mętnym podsumowaniem. Jego zapytania liczą się też do tych samych limitów użycia co główna sesja.
- **Nie zmierzyłem oszczędności.** Nie podam liczby tokenów ani minut, które dają te hooki. Mogę powiedzieć tyle: po kompaktowaniu kolejna tura zaczyna się od reguł, a nie od tego, że powtarzam je od nowa.

## Od czego zacząć

Najpierw krótki CLAUDE.md. Kolejny element dokładaj dopiero wtedy, gdy pojawi się jego sygnał: powtarzana poprawka, wklejany playbook, kopiowana karta przeglądarki, zalany kontekst, zasada, która musi działać zawsze. Jeśli dopiero zaczynasz, zajrzyj do przewodnika [Claude Code po polsku](/pl/blog/claude-code-po-polsku/). Jak te elementy zbudowały całą stronę, opisuję w [studium przypadku](/pl/blog/jak-powstala-ta-strona/), a same projekty znajdziesz na [stronie z pracami](/pl/work/).
